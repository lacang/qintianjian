## ① 逐项结论

### 1. 时区表（"部分错误"）

**1.1 现行偏移：基本正确。** 198 个内置城市逐个用 ICU/tzdata 校验 2026-01-15 与 2026-07-15 两个时点的真实偏移，只有 1 个错：

| 城市 | 表内 | tzdata 2026-07 | 结论 |
|---|---|---|---|
| 开罗 `Africa/Cairo` | std 2 / `dst:'none'` | 7 月 = **3** | **错 1 小时** |

埃及 2023 年经 24/2023 号法恢复夏令时（4 月最后一个周五 → 10 月最后一个周四），2026 年实际为 4/24–10/29。表里把埃及标成"无夏令时"，**所有 2023 年以后出生的埃及出生时间都会早 1 小时**。

**1.2 半小时/三刻时区全部正确**（这是任务点名的重点，逐条实测）：

| 城市 | 偏移 | 结论 |
|---|---|---|
| 新德里 / 孟买 `Asia/Kolkata` | 5.5 | 正确，非整数 |
| 加德满都 `Asia/Kathmandu` | 5.75 | 正确（三刻） |
| 德黑兰 `Asia/Tehran` | 3.5 | 正确（伊朗 2022 年已废 DST，表里 `none` 正确） |
| 阿德莱德 `Australia/Adelaide` | 9.5 / 1 月 10.5 | 正确（南半球 DST） |
| 达尔文 `Australia/Darwin` | 9.5，无 DST | 正确 |
| 仰光 `Asia/Yangon` | 6.5 | 正确 |

**1.3 DST 规则引擎本身可靠。** 对 13 个城市×年份（柏林/纽约/芝加哥/丹佛/悉尼/阿德莱德/奥克兰/圣地亚哥/特拉维夫/伦敦/里斯本 2026，北京 1988/1990）**逐日扫描 365 天，偏移不一致 0 天**；再对全部夏令时切换日逐小时扫 2448 个钟面时刻，仅 10 个"拨快空档小时"（如 02:00 这一刻根本不存在）的处理口径与 tzdata 不同，且钟面→UTC 往返自洽（`wall == civil` 全部成立）。

**1.4 结构性缺陷（比单个错值更严重）：表里每个城市只有"一条现行规则"，没有历史版本。**
抽 12 个年份（1975…2026）× 1 月/7 月 扫描：**61 / 198 个城市至少有一个年份偏移错 1 小时**。而本产品的主要用途恰恰是"算几十年前的出生时间"。实测样例：

### 2. 中国夏令时 1986–1991（"正确"）

**2.1 6 年起止全部正确。** 用 tzdata 2026e 扫描 `Asia/Shanghai` 1985–1992 的全部偏移变化点，与 timeanddate 页面双向核对：

| 年 | 实现/测试 `CN_DST_WINDOWS` | tzdata 实际 | timeanddate | 判定 |
|---|---|---|---|---|
| 1986 | 05-04 ~ 09-14 | 05-03 18:00Z→05-04 02:00；09-13 17:00Z→09-14 01:00 | 5/4 02:00 ~ 9/14 02:00 | 对 |
| 1987 | 04-12 ~ 09-13 | 同 | 4/12 ~ 9/13 | 对 |
| 1988 | **04-17** ~ 09-11 | 同 | 4/17 ~ 9/11 | 对（我原先怀疑是 4/10，实测 tzdata 与 timeanddate 都支持 4/17，实现是对的） |
| 1989 | 04-16 ~ 09-17 | 同 | 4/16 ~ 9/17 | 对 |
| 1990 | 04-15 ~ 09-16 | 同 | —（tzdata 一致） | 对 |
| 1991 | 04-14 ~ 09-15 | 同 | —（tzdata 一致） | 对 |

**2.2 边界判定口径正确**：实现按"先假设是夏令时，用 `civil−1h` 得到标准时，再看该标准时是否落在窗口内"来判断（`chinaDstAppliesToCivil`）。这与"窗口按当地**标准时**定义"的史实一致（结束日 02:00 是对标准时而言，故夏令时钟面 01:00–02:00 那一小时才对应标准时 00:00–01:00）。

**2.3 任务要求的三点实测（1990-04-15）**：

```
1990-04-15 01:30 → inDst=false, offset 8, standard 01:30   （尚未拨快，正确）
1990-04-15 02:30 → inDst=true,  offset 9, standard 01:30   （空档小时，按 01:30 标准时，已文档化）
1990-04-15 03:30 → inDst=true,  offset 9, standard 02:30   （正确）
1990-09-16 01:30 → inDst=true,  offset 9, standard 00:30   （回拨前最后一小时，正确）
1990-09-16 02:00 → inDst=false, offset 8                    （正确）
```

**2.4 遗留口径问题（不是错，是"存疑"）**：
- **新疆**：tzdata 的 `Asia/Urumqi` 在 1986–1991 **没有任何夏令时**（1988-07-01 12:00Z → 18:00，即恒定 +6），而程序对"乌鲁木齐"套用全国 +8 且加夏令时。乌鲁木齐 1988-07-15 00:10 被算成 1988-07-14 20:54（−3h16m）。若用户填的是"新疆时间"，偏差会是 3 小时；若填北京时，则又多扣了 1 小时夏令时。文件头声称"一律 +8 官方时区"，但官方夏令时在新疆是否执行是另一件事，建议在 UI 上对新疆/西藏给明确提示，而不是静默套用。
- 空档/重复小时的处理是"任选一个"，已文档化，可接受；但**没有把"该钟面时刻不存在"作为 warning 抛给界面**。

### 3. 真太阳时（"正确"）

**3.1 均时差 EoT：与 NOAA 闭式公式全年逐日对照，最大偏差 0.07 分。**

```
2026 全年 365 天：impl vs NOAA 闭式，max|Δ| = 0.07 分
2026 极值：最小 −14.16 分（2/11）  最大 +16.46 分（11/3）
```
与天文年历公开值（2 月中约 −14.2、11 月初约 +16.4）一致，量级与正负号都对。

**3.2 "用了哪个年度的 EoT"——按传入日期实时算，不存在跨年错用。** `equationOfTimeMinutes(date)` 走 `astronomy-engine` 的 `Equator(Body.Sun, date, …, true, true)`（视赤经）+ 该时刻的平太阳黄经，`EoT = 4min × (L0 − α)`。实测同一"月日"不同年份确实给出不同值（1950/1988/2026 的 11-03 分别为 +16.3x/+16.4x/+16.46），**没有拿当前年太阳位置算历史日期的问题**。"偶年误差"不适用——它用的是天文历表而非近似年表。

**3.3 经度时差符号正确。** 抽 8 城 × 4 日期 = 32 组，与独立口径"视太阳时 = UT + 经度×4 分 + NOAA EoT"对照：**最大偏差 0.07 分**（要求 ≤1 分）。符号抽查：

- 北京 lon 116.41（中央经线 120）→ 经度差 **−14.4 分**（真太阳时慢），2024-06-15 12:00 → 真太阳 11:45；
- 纽约 lon −74.01（中央经线 −75）→ **+4.0 分**（快）；
- 乌鲁木齐 lon 87.62 → **−129.5 分**（慢 2h09m）；
- 喀什 lon 75.99 → **−176.0 分**（慢 2h56m）。

全部符号正确（东经偏西为负、西经偏东为正）。

**3.4 与精确算法的一致性边界**：实现把 `L0 − α_apparent` 当作 EoT，严格定义还应含章动/光行差的高阶项，实测差异 < 0.1 分，对分钟的排盘无影响。

### 4. 跨日处理（"正确"，且没有双重扣减）

**4.1 无双重扣减。** 用一个能分辨"扣一次/扣两次"的用例（1988-07-15 15:10 北京，夏令时 + 真太阳时）：

```
15:10 (民用) −1h(DST) = 14:10 (标准) −21.2min = 13:49  → 未时
八字返回 时柱「乙未」（未时）✓
若 double-count 会得 12:49 → 午时「甲午」✗
```
即 `timeContext` 折一次，`bazi` 内部只做"按 23:00 换日"的换日，**不再重复扣夏令时**（`bazi.ts:147` 拿到 `eff.civil` 后直接 `Solar.fromYmdHms`，未再调 `solarToSiZhu`）。

**4.2 四类跨日全部正确**：

| 场景 | 输入 | 折算后 | 四柱 | 判定 |
|---|---|---|---|---|
| 乌鲁木齐（−2h09m） | 2024-06-15 00:30 | 2024-06-**14** 22:20 | 己酉 / 乙亥 | 正确回退一日 |
| 喀什（−2h56m） | 2024-06-15 02:00 | 2024-06-**14** 23:03 | 庚戌 / 丙子（23:00 换日进次日） | 正确 |
| 广州（−27m） | 2024-06-15 00:20 | 2024-06-14 23:53 | 前一日 + 子时 | 正确 |
| 东京（+18.8m+EoT+16.4） | 2024-11-03 23:40 | 2024-11-**04** 00:15 | 壬申 / 庚子 | 正确推进一日 |
| 东京 | 2024-02-11 23:50 | 2024-02-11 23:54 | 丙午（=2/12 日柱） | 正确（23:00 换日） |
| 安克雷奇（−8, DST） | 2024-06-15 00:10 | 2024-06-14 22:09 | 己酉 / 乙亥 | 正确 |
| 乌鲁木齐 + 夏令时 | 1988-07-15 00:10 | 1988-07-14 20:54 | 庚午 / 丙戌 | 只扣一次 −1h 与一次 −2h09m |

**4.3 紫微与八字口径一致**：同一跨日输入（乌鲁木齐 2024-06-15 00:30），`paiBazi` = 己酉/乙亥，`paiZiwei` 内部日期 2024-06-14、亥时、日柱 己酉，**两模块没有各自再折一次**。

**4.4 但存在跨模块口径不一致（隐患，非本次回归）**：六爻层 `solarToSiZhu`（`calendar.ts`）**只还原夏令时、不做真太阳时、也不认境外时区**。同一时刻两模块给出不同时柱：

```
北京 1988-07-15 12:00   八字 癸巳(10:39)  六爻层 甲午(11:00)
乌鲁木齐 2024-06-15 12:00 八字 辛巳(09:49)  六爻层 壬午(12:00)
```
凡出生时间落在时辰边界 ±20 分内，用户会看到"八字"和"六爻"两个不同的时柱，且无任何说明。

### 5. 向后兼容（"有严重漏洞"）

**5.1 触发条件过宽，且"只给经纬度"会静默兜底 +8。** `timeContext.ts:841`：

```ts
const hasTzHint = input.city != null || input.place != null || num(input.utcOffsetHours);
const hasGeo = num(input.lat) || num(input.latitude) || num(input.lon) || num(input.lonEast) || num(input.longitude);
```

只要 `lat`/`longitude` 之类的**任一**字段存在就进入折算；而 `resolveTime` 查不到城市时按 +8 兜底（`:706-709`，仅 push 一条 warning 字符串）。结果：

```
输入 {lat:40.7128, lon:-74.006}（纽约，未给城市/时区）
→ tz=+8, tzFallback=true, 经度差 −776 分
→ 1994-08-01 11:45 折算成 1994-07-31 22:42（跨日 + 差 13 小时）
输入 {latitude:40.7, longitude:-74}（旧字段名）
→ 2024-06-15 12:00 折算成 2024-06-14 23:03
```

这是**最危险的一条**：改造前 `bazi`/`ziwei` 完全忽略经纬度，老调用方（分享码、脚本、第三方按 `latitude/longitude` 传参）传了几何坐标是"无害的"；改造后同样的调用会被静默折算 13 小时。文件里 `:398` 的注释还写着"由调用方决定兜底策略，别在这里悄悄给 +8"，与 `:706` 的实际行为自相矛盾。

**5.2 前端活路径 1：手动指定时区会保留旧经纬度，产生 13 小时偏移。** `app/js/astroview.js:203-207`：

```js
const keep={};  // 只保留 lat/lon，不保留 city
if(Number.isFinite(cur.latitude)){ keep.lat=...; keep.latitude=...; }
if(Number.isFinite(cur.longitude)){ keep.lonEast=...; keep.longitude=...; }
setGeoOverride({ ...keep, city:null, place:`手动时区 ${offLabel(n)}`, utcOffsetHours:n });
```

用户默认出生地是沈阳（lon 123.43），一旦选"手动时区 −5"（想表示纽约），经纬度仍是沈阳的：

```
1994-08-01 11:45 + utcOffsetHours=−5 + lon=123.43
→ 经度差 +793.7 分（13.23 小时），真太阳时 1994-08-02 00:52
→ 四柱 甲戌 辛未 庚申 丙子   （正确的纽约：甲戌 辛未 己未 己巳）
```
**日柱都变了**。缺城市是 1.5 节的已知缺口（没有 −3:30、+10 等），用户"只能"走手动时区，等于必然踩这个坑。

**5.3 前端活路径 2：本命2（b2）继承主盘的时区。** `app/js/astroview.js:448-450` 与 `astromodes.js:156-161`：

```js
const city = CITIES.find(c=>c.name===b2.city) || CITIES[0];
return { ...base, ..., lat:city.lat, lonEast:city.lonEast, place:city.name };  // 没有 city 字段
```
`base` 是主盘的 `birthArgs()`，**`base.city` 被原样带过来**（查表优先级 city > place），而经纬度换成了 b2 的：

```
主盘 city=纽约，b2 选广州 1990-03-20 09:00
→ tz=−4（纽约 8 月夏令时）＋ lon=113.26（广州）
→ 折算成 1990-03-20 20:25（戌时），正确应为 08:33（辰/巳）
```

**5.4 其它兼容面（已验，无问题）**：
- 完全不传地点/经纬度 → `applied=false`，原样返回，与旧行为逐字节一致（`:848`）；
- `city` 查不到但 `place` 查得到 → 正确回落到 place（`{city:'火星',place:'纽约'}` → −4）；
- 显式 `utcOffsetHours` 优先，且**不再叠加**该城市的夏令时（`{city:'纽约', utcOffsetHours:9}` → 9），符合"显式值已含夏令时"的约定；
- `trueSolarTime:false` 时只给标准时，`trueSolar` 为 null；
- 无经度时不硬算真太阳时，只给标准时 + warning。

**5.5 警告没有出口。** `civilForPaipan` 返回了 `resolution.warnings`，但 `paiBazi`/`paiZiwei` 都不透传（两文件里 grep 不到 `warnings`），前端 `baziview.js`/`ziweiview.js` 也没有任何"真太阳时/夏令时/兜底"字样。也就是说 §1.4、§5.1、§5.3 这些错**在八字/紫微界面上是完全不可见**的，只有星盘页显示兜底提示。

- `境外 DST：美/欧/澳/新 起止`（法规事实，我用 tzdata 逐日扫过，0 天不符）

**半独立（10 条）**——事实正确但常量是从实现里抄出来的，只能防"以后改坏"，不能防"一开始就错"：
- `CN_WINDOWS` 六行表（`:227` 注释自称"timeanddate 逐年核对"）。测试用 `chinaDstWindow(year)` 与这张表逐字比对——**表若错，两边一起错**。我另用 tzdata + timeanddate 验证：这六行恰好是对的。
- `1988 起点 04-17`、`1986 起点 05-04` 等边界日断言（同上，来源同一张表）。
- `sourceTzName === 'Asia/Shanghai'`（拿表的 IANA 字符串自证，未与"该字符串是否是有效 IANA 名"分开检）。

**循环论证（8 条）**：
- `真太阳时三份口径自洽（:83-90）`：`standard + 经度差 + EoT ≟ trueSolar`，三个量全部取自同一个返回对象，**只要实现内部引用一致就永远通过**，无法发现公式错。
- `longitudeOffsetMinutes ≈ 13.73`（沈阳）= `4×(123.4315−120)`，用表里的 lon 算表里的 lon 差。
- `trueSolarOffsetMinutes ≈ 13.19` = 上一条 + EoT，纯加法。
- `minutesOfDay(trueSolar) === 12*60+13`：由上面两常量推出，非独立观测。
- `拉萨 −115.31 / 乌鲁木齐 −129.53 / 喀什…`：同类。
- `r.utcMs === bj.utcMs`（"同日同时刻 UTC 相同"）：同城市自身对比。
- `formatOffsetName(8/−3.5/5.75)`：格式函数对自身输出的格式断言。
- `dstWindow.startLocal === '1988-04-17 02:00'`：窗口对象直接来自被测函数。

**把缺陷写成预期（2 条，最需要改）**：
- `:199-205「查不到城市时兜底 +8 并打 tzFallback 标记」`：用**伦敦坐标** `{lat:51.5, lon:-0.12}` 断言 `utcOffsetHours === 8`。这等于把 §5.1 的静默错固化成"正确行为"，未来谁修这个 bug 谁弄红测试。
- `paipan-tz-wiring.test.ts:42-45「纽约出生不能按 +8 算」`：只断言"两组四柱不相等"，**不校验等于什么**；把 +8 换成 +9 也能通过。

**测试完全没覆盖的（这才是重点）**：
1. 任一城市 2023 年之后的现行规则（开罗错值至今绿）；
2. 任一城市 1975–2020 的历史规则（61 城错值至今绿）；
3. `lat/lon` 无 `city` 的兜底行为（只有"伦敦坐标→+8"这条，且被当作正确）；
4. 手动时区 + 旧经纬度的组合；
5. `b2` 继承主盘 city 的组合；
6. 八字/紫微是否把 `warnings` 透传到界面。

## ③ 未验证 / 存疑（明确标注）

1. **198 个城市的经纬度没有逐个核对**。只做了三类间接检查：①与中央经线偏差 >20° 的仅 5 城（乌鲁木齐/喀什/拉萨/卡萨布兰卡/雷克雅未克，均合法）；②坐标无越界、无重复；③时区字段与 IANA 名全部有效。**具体城市坐标若有个位数错误（如 1° 偏差 ≈ 4 分钟），本报告发现不了。**
2. **NOAA 对照用的是闭式公式，不是 NOAA 在线计算器逐点比对**。两者理论差 <0.5 分，实测 <0.07 分；但没有对 6 城×4 日期逐条抓取 timeanddate 的"solar noon"页面做第三方锚定（只抓了中国 DST 与埃及 DST 两处）。
3. **`圣地亚哥 2015-07` 的 tzdata 结果（−3）与我预期（−4）不符**，未进一步用智利官方法规核实；该行在 F5 表里标了"存疑"，不作为缺陷计数。
4. **未在真实浏览器里跑前端**。§5.2/§5.3 是"按 `astroview.js` 源码复刻参数"用 Node 调核心得到的数字，没有点击验证 DOM 流程；结论依赖"`setGeoOverride` 只在这两处被调用"这一 grep 结果（`app/js` 内共 2 处调用 + 1 处定义）。
5. **未验证 1900 年前 / 未来年份**（表内规则无年份上下界断言）、**未验证闰秒**、**未验证 `astro`/`vedic` 的宫位换算是否也用同一 UTC**（只确认 `astro.ts` 不在真太阳时上叠加一次）。
6. **未审计 `solartime.js`（前端 `toTrueSolar`）**——这是起卦/起盘时刻的另一套真太阳时实现，与核心 `timeContext` 是否同源未查。若两套算法不一致，会出现"起卦时刻"与"八字时刻"口径分裂。
7. 未跑性能/边界模糊测试（极北纬度、±180° 经线附近城市）。

## 附录：建议修复方向（**未改代码，等批准**）

按性价比排序：

1. **`hasGeo` 不应单独触发折算**：只有 `lat+lon` 而无 `city/place/utcOffsetHours` 时，(a) 直接 `applied=false` 保持旧行为，或 (b) 抛错要求补时区。绝不能静默 +8（同时改掉 `:199` 那条把缺陷当预期的测试）。
2. **手动时区时清空经纬度**，或当 `|lon − 15×offset| > 12h` 时拒绝折算并提示——这能同时挡住 F3、F4。
3. **`b2ArgsOf` 显式传 `city: city.name`**（并把 `place` 一起覆盖）。
4. **开罗补 `dst:'EG'` 规则**（4 月最后周五 00:00 → 10 月最后周四 24:00）；顺带评估是否给表加"规则生效年份区间"，至少对历史规则未覆盖的国家输出 warning（现在只对 EU/US/AU）。
5. **`paiBazi`/`paiZiwei` 透传 `resolution.warnings`，界面显示**"已按真太阳时 10:39 排盘 / 已还原 1988 夏令时 / 时区兜底 +8"。
6. **统一六爻层口径**：让 `solarToSiZhu` 也能吃 `city/lon`（或明确在界面标注"六爻按北京时间"）。
7. 测试补三条差分用例：①任一城市历史年份 vs tzdata 期望表；②`lat/lon` only 的兜底拒绝；③手动时区 + 旧坐标。
