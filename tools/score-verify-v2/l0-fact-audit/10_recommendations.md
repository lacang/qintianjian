## 2 逐项建议

### 2.1 P1：修 `BAGUA_BITS`（ISSUE-L0-002）

**位置**：`liuyao-core/src/constants.ts`

**改法**：

```ts
// 现状（错）
兑: [false, true, true],   // 011
震: [false, false, true],  // 001
巽: [true, true, false],   // 110
艮: [false, false, true],  // 001  ← 与震完全相同，这一处本身就是硬 bug

// 应改为（自下而上，与 XIANTIAN_LINES 口径一致）
兑: [true, true, false],   // 110
震: [true, false, false],  // 100
巽: [false, true, true],   // 011
艮: [false, false, true],  // 001
```

**为什么必须和 `XIANTIAN_LINES` 对齐**：`timecast.ts:XIANTIAN_LINES` 里同一批 8 卦的表示是**正确的**，且时间起卦依赖它算出的卦是对的（U 系列已验证时间起卦的卦名 100% 正确）。这说明项目内部已经有一份正确表，`BAGUA_BITS` 是另一份抄错表。**修的时候应以 `XIANTIAN_LINES` 为准绳**。

**验证方式**：
1. `node tools/score-verify-v2/l0-fact-audit/scripts/03_ui.mjs` → U1 应 8/8
2. `bash tools/build-vendor.mjs` 重打 vendor（否则 `app/vendor/liuyao-core.js` 仍是旧值）
3. `bash tools/gates.sh` 12 步门禁
4. 手动打开一卦，开"显示藏爻"，看兑宫卦的藏爻列是否变成 ☱

**风险**：`getShouGuaPan` 全项目只有 1 个调用点（`panview.js:59`），只用于生成藏爻列，**不参与任何计算**。grep 已确认 `verdict.js` 完全不引用。所以零回归风险。

**注意**：这条修改会让"藏爻列"的显示变化，但**藏爻的六亲/干支不变**（U2 已 48/48 正确），所以看盘结论不变。

### 2.2 P2：雷火丰归魂/世位（ISSUE-L0-001）

**这是本轮唯一需要主人做"体系选择"的问题，不能技术拍板。**

三个方案：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 全取现用 App 口径 | `GUI_HUN_OVERRIDE` 扩展为同时改世应：雷火丰 → 世3应6 | 与主人现用 App 完全一致 | 破坏八宫结构（坎宫第 6 卦世 3，则第 3 卦的世位映射也乱），`SHI_OF_XU` 映射失效，牵动面大 |
| B 全不取（回归古法） | 删除 `GUI_HUN_OVERRIDE`，雷火丰 = 五世、不标归魂 | 内部完全自洽，《增删卜易》行 976 支持 | 与主人现用 App 显示不一致，若主人习惯按 App 看会困惑 |
| C 保留现状 + 加注 | 标签显示「（归魂·世五）」或「（五世）」并附一行说明 | 最小改动、不误导 | 仍是"两套体系混用" |

**建议倾向 B**。理由：
1. 古法依据明确（行 976「归魂卦为各宫之第八卦」）
2. 项目其余 63 卦全部按古法八宫结构，只有这 1 个例外，反而破坏了"可溯源"这条铁律
3. 主人铁律里写了"流派分歧并列不合成"——现在是"合成"了（归魂取 App、世位取古法）
4. 若主人确实依赖 App 口径，可以做成开关，但不要默认混合

**若选 B 需要确认**：主人现用 App 里雷火丰到底显示什么？如果 App 显示"归魂·世五"，那 App 本身也是混的，那就更该选 B。

### 2.3 P3：真太阳时（ISSUE-L0-007）

**需要主人确认一件事**：`cfg.apparentSolarTime` 的默认值是 `true` 还是 `false`？

- 若默认 `true`：建议在 `pan-head` 加一行 `（真太阳时 +29.6分）`，让用户知道日柱可能不是按钟表算的
- 若默认 `false`：建议在设置页说明"开启后日柱可能跨日"

**不建议改算法**。真太阳时是正当流派，问题只是"用户是否知道时间被移动了"。

### 2.4 P4：天机起卦概率（ISSUE-L0-004）

**需要主人裁定一件事**：希望"天机起卦"是

- (a) 独立的随机方式，与摇钱不同（现状：四象均匀，动爻率 50%）
- (b) 与摇钱概率可比的随机方式（改二项分布，动爻率 25%）

**若选 (b)**，改法：

```ts
// input.ts castTianji 内，把均匀四象改为背数二项分布
// 现状
const v = [6,7,8,9][Math.floor(rng() * 4)];

// 改为
const backs = (rng() < 0.5 ? 1 : 0) + (rng() < 0.5 ? 1 : 0) + (rng() < 0.5 ? 1 : 0);
const v = YANGS_TO_VALUE[backs];   // [6,7,8,9]
```

改动约 5 行。**但会改变所有历史天机盘的性质**，需主人明确同意。

**我的倾向**：选 (a) 不改。理由——天机起卦本来就不是摇钱，用户选"天机"就是要一个不同的随机；强行对齐摇钱概率反而抹掉了这个选项的意义。真正的问题是**没有告知用户两种方式的动爻率差异**，可以在起卦页加一行说明。

## 4 下一轮（L1）需要 L0 提供的口径事实

以下是从本轮结论直接带进 L1 的输入，请 L1 审计时按此口径：

1. **变爻六亲 = 本卦宫五行**（不是变卦自身宫）
2. **旬空 = 日旬空**（无时旬空）
3. **归魂/游魂标记**：除雷火丰外，其余 63 卦按古法八宫；雷火丰待裁定
4. **六亲齐全度**：仅 20/64 卦五亲齐全，69% 的卦需要走伏神路径 → L1 的用神规则必须能处理"用神不现 → 取伏神"
5. **起卦方式概率差异**：天机动爻率 50% vs 摇钱 25% → L1 统计"变卦类规则触发率"时不能用摇钱的先验
6. **真太阳时可跨日**：22:40–23:00 区间起卦需注意日柱
7. **节气精度 ±120s**：交节前后 1 分钟内的盘，月柱归属存在流派空间
