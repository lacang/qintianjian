## 2. 独立预期的构造方式（为什么这些数字可信）

## 3. 唯一差异：雷火丰的「归魂」标签

| 项 | 独立预期 | 项目输出 |
|---|---|---|
| 八宫序 | 6（坎宫第六卦） | 6 ✅ |
| 世位 | 5（五世卦） | 5 ✅ |
| 应位 | 2 | 2 ✅ |
| `isYouHun` | false | false ✅ |
| `isGuiHun` | **false** | **true** ❌ |
| `isBaChun` | false | false ✅ |

**这不是算错，是主动覆盖。** `constants.ts` 的 `GUI_HUN_OVERRIDE` 注释原文说明：主人现用的「六爻排盘」App 把雷火丰标为"坎宫归魂（世五应二）"，而 mingpan / tsumugi / 通行京房体系均作"坎宫五世卦"。项目决定"以金标准为准"，只覆盖魂卦标记、**不改世应**。

**产生的后果**：盘面头部会显示「坎宫：雷火丰（归魂）」，但世爻在第 5 位。而古法归魂卦的世位**定义上就是第 3 位**（《增广贤文》体系：归魂世三、游魂世四）。所以盘面同时呈现「归魂」与「世五」，**在古法内部是自相矛盾的**。

**《增删卜易·归魂游魂章》原文**（底本行 976）：

> 游魂卦为各宫之第七卦……归魂卦为各宫之第八卦

按此定义，归魂卦必须同时满足"第八卦"与"世三"。雷火丰是第六卦，若标归魂则世位应为 3；若保留世 5 则不应标归魂。**二者只能取一个。**

**影响范围**：
- 不产生计算错误（世应数值本身正确，纳甲六亲全对）
- 影响 `panview.js` 头部标签文案（用户可见）
- **不影响 verdict.js 的吉凶评分**（`verdict.js` 不使用 `isGuiHun`，已 grep 确认）
- 影响用户对"这是归魂卦"的认知，进而可能自己套用归魂的断法

**登记为 F1（卦象结构）+ F6（流派差异）**，需主人裁定。见 09 文档 ISSUE-L0-001。

## 4. 动变层：384 个单动 + 24 个多动，零差异

| 子项 | 用例 | 差异 | 说明 |
|---|---|---|---|
| 变卦名 | 384 | 0 | 64 卦 × 6 个单动爻，变卦名全部与独立预期一致 |
| 动爻位 `movingPositions` | 384 | 0 | 数组内容与顺序均正确 |
| 变爻纳甲 | 384 | 0 | 变卦该爻位的干支按变卦上下卦取纳甲，全部正确 |
| 多动（2 动 / 5 动 / 6 动 / 2 动×2） | 24 | 0 | 4 个基础卦 × 6 种动爻组合 |
| 静卦无变卦 | 2 | 0 | `bianGua` 为 null |

**变爻六亲的口径（重要，但非缺陷）**：

```
按变卦自身宫五行推六亲：144/384 吻合
按本卦宫五行推六亲：    384/384 吻合  ← 项目实际采用
```

`paipan.ts` 有明确注释说明"变卦六亲恒用本卦宫五行"，这是项目主动选择的口径（通行六爻实务中两种做法都有：一种以本卦宫为"我"贯穿全盘，一种变卦另起宫位）。**登记为 F6 流派差异，不是错误**，但需注意：若用户对照的 App 用"变卦自身宫"口径，会看到六亲不一致。

## 5. 起卦三方式

### 5.1 摇铜钱（`castCoins`）

```js
const YANGS_TO_VALUE = [6, 7, 8, 9];   // 背数 0/1/2/3
backs = coins[0] + coins[1] + coins[2];
```

| 背数 | 古法名称 | 爻值 | 是否符合京房钱法 |
|---|---|---|---|
| 0（三字） | 老阴（动） | 6 | ✅ |
| 1（一背两字） | 少阳 | 7 | ✅ |
| 2（两背一字） | 少阴 | 8 | ✅ |
| 3（三背） | 老阳（动） | 9 | ✅ |

**结论：完全符合京房钱法。** 且 `normalize()` 强制校验 6 爻、值域 {6,7,8,9}，非法输入抛错——显式失败，符合项目契约。

**概率分布**（真实摇钱，每枚硬币 1/2）：

| 结果 | 理论概率 | 动爻? |
|---|---|---|
| 老阴 6 | 1/8 = 12.5% | 是 |
| 少阳 7 | 3/8 = 37.5% | 否 |
| 少阴 8 | 3/8 = 37.5% | 否 |
| 老阳 9 | 1/8 = 12.5% | 是 |
| **单爻动概率** | **25%** | |
| **6 爻全静概率** | (3/4)^6 = **17.8%** | |

### 5.2 手录（`castManual`）

阴阳 + 是否动 → 7/9/6/8，映射正确，无概率问题（用户自定）。

### 5.3 天机随机（`castTianji`）

```js
// 每爻先按四象均匀（6/7/8/9 各 25%）。调用方若希望限制动爻数可自行重投，
// 本函数不做人为干预（金标准未限定天机起卦的动爻概率分布，均匀最中立）。
```

**概率对比（这是本轮的一个量化发现）**：

| 指标 | 真实摇钱 | 天机起卦 | 倍数 |
|---|---|---|---|
| 单爻动概率 | 25% | **50%** | 2.0× |
| 6 爻全静概率 | 17.8% | **1.56%** | 0.088× |
| 期望动爻数 | 1.5 | **3.0** | 2.0× |
| 出现变卦的概率 | 82.2% | **98.4%** | 1.20× |

**后果**：天机起卦几乎必然产生变卦（98.4%），而真实摇钱有 17.8% 是静卦。这直接影响 `verdict.js` 中所有依赖"变卦"的规则触发频率（如"六冲变六合 +2"、"六合变六冲 −2"、"用神化回头克"等）。

**判定**：注释已明示这是主动设计（"金标准未限定，均匀最中立"）。**登记为 F6 设计差异**，不算错误。但需要主人知道：**同一件事，用摇钱和用天机起卦，得到变卦的概率差 1.2 倍，得到"化回头克"这类变卦类凶象的概率也相应升高。** 若希望两种方式可比，应把天机起卦改为按真实二项分布（背数 ~ B(3, 0.5)）。

### 5.4 时间起卦（`castByTime`，梅花易数）

```js
sum = 年支序 + 农历月 + 农历日
上卦 = sum % 8（0→8）
下卦 = (sum + 时支序) % 8（0→8）
动爻 = (sum + 时支序) % 6（0→6）
XIANTIAN_LINES = { 1:乾111, 2:兑110, 3:离101, 4:震100, 5:巽011, 6:坎010, 7:艮001, 8:坤000 }
```

**核对结果**：

| 检查项 | 结论 |
|---|---|
| 先天卦序（乾一兑二离三震四巽五坎六艮七坤八） | ✅ 与 `XIANTIAN_LINES` 完全一致 |
| 上卦 / 下卦 / 动爻三个公式 | ✅ 与梅花易数通行法一致 |
| 晚子时 23:00 处理（`hh===23` 时农历进次日，时支仍取本时刻） | ✅ 与日柱口径一致 |
| 输出 yaoValues 合法性 | ✅ 400/400 次随机时间全部落在 {6,7,8,9} 且动爻数恰为 1 |

**注意**：`XIANTIAN_LINES`（正确）与 `constants.ts:BAGUA_BITS`（4 卦错）是**两张不同的表**，前者用于时间起卦、后者用于藏爻列。前者正确，所以时间起卦结果不受影响。这是为什么 T1b（时间起卦自洽）能 400/400 通过，而 U1（藏爻阴阳）有 4 宫错——**两张表必须分开看，不能因为一处对就认为另一处也对**。

## 6. 本节结论

卦象结构层 **1080 例，1079 通过**。唯一差异是雷火丰的归魂标签覆盖（设计选择，但与世位自相矛盾，需裁定）。

动变层 792 个变卦全部零差异，变爻纳甲零差异。变爻六亲用本卦宫五行是主动设计。

起卦三方式中，摇钱映射完全符合京房钱法；时间起卦公式与梅花易数通行法一致；**天机起卦的四象均匀分布与真实摇钱概率不同（动爻率 2 倍）**，是需要主人知道的设计差异。
