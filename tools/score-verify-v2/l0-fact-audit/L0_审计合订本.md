## 第 1 章　L0 历法与排盘事实层审计

> 原文件：`README.md`

> 本轮只回答一个问题：**钦天监算出来的历法、卦象、纳甲、六亲、世应、六神、伏神、旬空、动变，这些"事实"到底对不对？前端展示与计算结果是否一致？**
>
> 不审计吉凶评分、古法规则适用、机器解卦。不修代码。不提交。不推送。不部署。

## 一、结论摘要

| 层 | 用例数 | 通过 | 差异 | 判定 |
|---|---|---|---|---|
| L0-A 历法（四柱/旬空/子时/节气边界） | 598 | 598 | 0 | **可靠** |
| L0-B 卦象结构（64 卦名/宫/世应/纳甲/六亲/六神/伏神/动变/卦身） | 3826 | 3825 | 1 | **可靠，1 处已登记的设计覆盖** |
| L0-C 前端展示一致性 | 117 | 112 | 5 | **1 处真实缺陷 + 1 处自相矛盾标签** |
| **合计** | **4541** | **4535** | **6** | — |

三句话结论：

1. **排盘事实层是可靠的。** 64 卦 × 6 爻 = 384 个爻位的纳甲天干、纳甲地支、爻五行、六亲、世应、六神，以及 64 卦的卦名、上下卦、卦宫、宫五行、首卦名、伏神清单、飞伏关系、卦身，**全部零差异**；384 个单动变卦的变卦名、动爻位、变爻纳甲也**全部零差异**。历法层 598 例零差异，包括用独立天文算法（astronomy-engine 太阳视黄经）交叉验证的 96 例节气明确态、90+120 例日柱、60 例旬空。
2. **唯一一处真实缺陷在前端展示层，不在计算层。** `BAGUA_BITS` 表把「兑/巽」「震/艮」两对卦的阴阳写反，导致**藏爻列的阴阳爻线画错**（兑宫显示成巽宫的样子，反之亦然；震艮同理），影响 32 个卦，但**只在用户打开"显示藏爻"时可见**，且**不影响六亲、干支、世应、旺衰、吉凶评分**（verdict.js 不使用藏爻）。
3. **一处内部自相矛盾需要裁定，但不是算错。** 雷火丰被标为「归魂」却仍用「五世」的世应位——这是项目为对齐主人现用 App 而做的 `GUI_HUN_OVERRIDE` 覆盖，注释已明示，属于"取了标签没取世位"的折中。它不产生计算错误，但会产生**盘面自相矛盾的展示**。

## 三、独立验证原则的落实

任务书要求「禁止用被测函数自己生成的结果作为唯一证据」。本轮所有预期值来源：

| 审计项 | 预期值来源 | 与被测实现的关系 |
|---|---|---|
| 节气时刻 | astronomy-engine 2.1.19 `SunPosition().elon` 二分求解太阳视黄经 315°/345°/…/285° | **完全独立的第三方天文库**，不是 lunar-javascript 的依赖 |
| 日柱 | 儒略日数公式 `index = (JDN + 49) mod 60`，锚点 1900-01-01 = 甲戌、2000-01-01 = 戊午 | 纯算术，不调用任何历法库 |
| 年柱 | 立春为界 + `(年-4) mod 60` | 用自算立春，不用库的节气表 |
| 月柱 | 太阳视黄经 30° 区间定月支 + 五虎遁定月干 | 自算 |
| 时柱 | 钟点定时支 + 五鼠遁定时干 | 自算 |
| 旬空 | 日干支 → 旬首 → 后两位地支 | 自算 |
| 卦名 | 8×8 标准卦名表（上卦×下卦） | 手写固定表 |
| 卦宫/世应/游魂/归魂 | 由「本宫→一世→…→五世→游魂→归魂」变爻规则**现场生成**，不用现成表 | 自算 |
| 纳甲 | 八卦纳甲口诀（内三爻/外三爻） | 手写固定表 |
| 六亲 | 以宫五行为「我」，生我父母/我生子孙/克我官鬼/我克妻财 | 自算 |
| 六神 | 日干起法（甲乙青龙…壬癸玄武） | 自算 |
| 伏神 | 本宫首卦中本卦所缺六亲，伏于同爻位 | 自算 |
| 卦身 | 阳世从子起、阴世从午起，数世位-1 | 自算 |

唯一无法独立验证的是**节气时刻本身的绝对正确性**（需要更高精度天文历表做基准）。本轮改用「量化两套算法偏差」的方式处理：astronomy-engine 与 lunar-javascript 在 44 个节气切换点上最大偏差 120 秒、中位 60 秒，属分钟级精度差，不构成排盘错误（详见 03 文档 §4）。

## 4. 节气时刻：两套独立算法的偏差量化

**这是本轮唯一"无法完全裁定"的项，处理方式是量化偏差而非判对错。**

- 被测：lunar-javascript 1.7.7 的节气表
- 基准：astronomy-engine 2.1.19 `SunPosition().elon`（地心视黄经）二分求解 15° 整数倍时刻，精度 1 秒
- 方法：对 2024–2027 每年 12 个「节」中的 11 个（立春单独用于年柱），在 ±30 分钟窗口内**二分实测 lunar-javascript 的月柱切换点**（分钟精度），与基准比较

**结果（44 个切换点全部可测）**：

| 指标 | 值 |
|---|---|
| 最大绝对偏差 | **120 秒** |
| 中位绝对偏差 | **60 秒** |
| 偏差方向 | 双向（lib 有时早、有时晚） |

最大偏差 3 例：

| 节气 | 基准（astronomy-engine） | 实测（lunar-javascript） | Δ |
|---|---|---|---|
| 2024 立冬 | 2024-11-07 06:19 | 2024-11-07 06:21 | +120s |
| 2024 大雪 | 2024-12-06 23:16 | 2024-12-06 23:18 | +120s |
| 2027 立夏 | 2027-05-06 01:24 | 2027-05-06 01:26 | +120s |

**判定**：分钟级精度差，来源是两套算法对「视黄经 vs 平黄经」「章动/光行差修正项」的不同取舍，属正常工程误差。**对排盘的实际影响**：仅在交节前后 1–2 分钟内起卦的极端情况下，月柱可能差一个月。这个概率量级约为 120s / (30 天 × 86400s) ≈ **0.005%**。

**为什么不判为缺陷**：
1. 古法本身对"交节当刻算不算下月"存在流派分歧，秒级精度无经典依据可依；
2. 要裁定谁对，需要 JPL DE 星历或紫金山天文台《中国天文年历》级别的基准，超出本轮范围；
3. 影响面 0.005%，且落在这个窗口内时两套算法都能自圆其说。

**登记为 F4**（依赖不可完全验证），不列为需修复项。

**独立基准自检**：astronomy-engine 算出的 2026 年立春为 **2026-02-04 04:01（北京时间）**，与公开历书一致；2024 年立春 16:26、2025 年立春 22:10 亦一致。基准本身可信。

## 5. 真太阳时对边界的影响（机制说明，非缺陷）

`toTrueSolar` 的改正量 = 均时差（年内 −14 ~ +16 分钟）+ 4×(经度−120) 分钟。

以沈阳（东经 123.4°）为例：经度项 +13.6 分钟；11 月初均时差约 +16 分钟 → **合计 +29.6 分钟**。

**后果**：北京时间 22:40 起卦，真太阳时约 23:10 → **跨入子时、日柱换日**。

这是真太阳时流派的必然结果，不是计算错误。需要确认的是：
- 摇卦/手录路径：`resolveCastDate` 在 `paipanZi` 之前生效 → 日柱按时辰校正后的时间算 ✅
- 天机路径：`applyTstAt(d)` 在 `castByTime` 之前生效 → 起卦数与时间都基于校正后时刻 ✅
- **但 `paipanZi` 拿到的 `castDate` 也是校正后的 `dt`**（`onCast(r.cast, 'tianji', dt)`）→ 排盘四柱同样用校正后时间 ✅ 一致

**唯一需要主人拍板的**：真太阳时开关默认值。若默认开启，则"钟表时间 22:40"会被排成次日子时——这会与用户心理预期不符。本轮只记录机制，不判定默认值对错。

## 3. 真实缺陷：藏爻列阴阳爻线画错（B 传递 + C 展示）

### 3.1 现象

| 宫 | 应有阴阳（八纯卦六爻） | 实际显示 | 结果 |
|---|---|---|---|
| 乾 | 111111 | 111111 | ✅ |
| **兑** | **110110** | **011011** | ❌ 显示成了巽 |
| 离 | 101101 | 101101 | ✅ |
| **震** | **100100** | **001001** | ❌ 显示成了艮 |
| **巽** | **011011** | **110110** | ❌ 显示成了兑 |
| 坎 | 010010 | 010010 | ✅ |
| **艮** | **001001** | **100100** | ❌ 显示成了震 |
| 坤 | 000000 | 000000 | ✅ |

**错误模式**：兑↔巽 整列互换、震↔艮 整列互换。即四对卦中的两对，藏爻列会画成"另一个卦"的样子。

### 3.2 根因

`liuyao-core/src/constants.ts` 的 `BAGUA_BITS`：

```ts
export const BAGUA_BITS: Record<BaGua, readonly [boolean, boolean, boolean]> = {
  乾: [true,  true,  true ],   // ☰ 111  ✅
  兑: [false, true,  true ],   // ☱ 应为 110，写成了 011（= 巽）
  离: [true,  false, true ],   // ☲ 101  ✅
  震: [false, false, true ],   // ☳ 应为 100，写成了 001（= 艮）
  巽: [true,  true,  false],   // ☴ 应为 011，写成了 110（= 兑）
  坎: [false, true,  false],   // ☵ 010  ✅
  艮: [false, false, true ],   // ☶ 应为 001，写成了 100（= 震）
  坤: [false, false, false],   // ☷ 000  ✅
};
```

**4 个卦写反，且恰好是两对互换**——这说明是抄表时把「自下而上」和「自上而下」两个方向混了：兑 ☱ 自下而上是「阳阳阴」=110，自上而下读是「阴阳阳」=011。震/艮、巽/兑同理。

**唯一使用点**：`paipan.ts:243` 的 `getShouGuaPan(gong)`：

```ts
const bits = BAGUA_BITS[gong];
// → 用于生成八纯卦六爻的 yinYang 字段
```

### 3.3 影响面（精确边界）

| 维度 | 影响 | 说明 |
|---|---|---|
| 藏爻列阴阳爻线 | ❌ 错 | 4 个宫 × 8 卦 = **32 个卦**（占 64 卦的一半） |
| 藏爻列六亲 | ✅ 对 | U2：48/48 通过（`getFullNajia` 取纳甲，不经过 `BAGUA_BITS`） |
| 藏爻列干支 | ✅ 对 | 同上 |
| 复制文本的藏爻段 | ❌ 错 | `panview.js:152` 传 `showHidden: cfg.showCangyao`，开启时同样错 |
| 本卦六爻阴阳 | ✅ 对 | 来自 `yaoValues`，不经过 `BAGUA_BITS` |
| 变卦六爻阴阳 | ✅ 对 | 同上 |
| 世应 / 六亲 / 六神 / 纳甲 | ✅ 对 | 384/384 |

**关键限定**：
1. 只在用户**打开"显示藏爻"开关**时才可见（默认关闭）
2. 只影响**阴阳爻线的画法**，同一行的六亲、干支是对的

虽然不影响吉凶，但它是一个**懂卦的人一眼就能看出的错误**。主人自用时会打开藏爻看伏神，兑宫/巽宫/震宫/艮宫的卦会看到"这卦画得不对"，直接损伤对整个盘面的信任。修复成本极低（改 4 个布尔值），收益是消除一个"看起来很不专业"的硬伤。

## 4. 头部标签自相矛盾：雷火丰「归魂 + 世五」

### 4.1 现象

```
实测输出：坎宫：雷火丰（归魂）        世爻在第 5 位、应爻在第 2 位
```

古法定义（《增删卜易·归魂游魂章》行 976）：

> 游魂卦为各宫之第七卦……归魂卦为各宫之第八卦

归魂卦 = 第八卦 = 世三应六。雷火丰是坎宫**第六卦**（五世），世五应二。

**盘面同时呈现「归魂」与「世五」，在古法内部不能并存。**

### 4.2 对照：真正正确的两个魂卦

| **雷火丰** | **6** | **归魂** | **世5 应2** | ❌ **矛盾** |

### 4.3 根因与已知性

`constants.ts:GUI_HUN_OVERRIDE` 注释原文（摘要）：

> 主人现用的「六爻排盘」App 把雷火丰标为"坎宫归魂（世五应二）"，而 mingpan / tsumugi / 通行京房均作"坎宫五世卦"。项目以金标准为准，只覆盖魂卦标记、不改世应。

即：项目**主动**取了 App 的"归魂"标签，但没取 App 的世应（因为世应改了会连带影响整个八宫结构和后续所有规则）。结果是拿到了一个**半截的覆盖**。

| 盘面专业性 | ❌ 矛盾肉眼可见 |

## 1. 测试空间定义

本轮三个脚本的测试空间，全部是**穷举或结构化覆盖**，不是随机抽样（随机只用于补充时间维度）。

### 1.1 `01_calendar.mjs` —— 历法空间

| 维度 | 取值 | 规模 |
|---|---|---|
| 日柱日期 | 2020-01-01 起连续 90 天 | 90 |
| 日柱日期（跨年抽样） | 2000–2035 随机 | 120 |
| 节气边界 | 2024–2027 × 12 节 × {节前 10min, 节后 10min} | 96 |
| 年柱边界 | 同上（立春为界） | 96 |
| 时柱 | 5 个不同日干 × 24 小时 | 120 |
| 子时边界 | {22:59, 23:00, 23:59, 00:00, 00:59, 01:00} × {日柱, 时柱} | 12 |
| 旬空 | 六十甲子全量 | 60 |
| 跨日跨年 | 4 个关键点 | 4 |
| **合计** | | **598** |

**时柱为什么 5 个日干就够**：五鼠遁以 `日干 % 5` 分组（甲己、乙庚、丙辛、丁壬、戊癸 各同组）。测试取的 5 个日干是连续日（如甲、乙、丙、丁、戊），`%5` 恰好遍历 0–4，**覆盖全部 5 个起法组**，因此 24 小时 × 5 组 = 120 例即完备覆盖时柱全部可能。

**日柱为什么 90 天够**：六十甲子 60 天一轮，90 天 = 1.5 轮，必然覆盖全部 60 个日干支 + 30 个重复验证。再叠加 120 个跨 35 年的随机日，覆盖闰年、月末、年末。

### 3.2 交叉验证的有效性

任务书要求「多个函数输出一致不等于正确，共用同一错误算法时交叉验证会失效」。

本设计对此的处理：

- **被测链**：`paipan()` → mingpan（纳甲/世应/六亲/六神/伏神）+ lunar-javascript（四柱/旬空）
- **独立链**：手写表 + 变爻规则 + JDN 公式 + astronomy-engine 天文计算

两条链**没有共享任何代码或数据表**。特别地：

- 纳甲：mingpan 内部实现 vs 我手写的八卦纳甲口诀 → 两套独立
- 卦宫：mingpan 的八宫表 vs 我用变爻规则现场生成 → 两套独立（如果 mingpan 内部也是查表，我的生成法能发现表错；如果它也是生成法，则两者独立实现同样能互相校验）
- 日柱：lunar-javascript vs JDN 公式 → 完全不同的算法族

**唯一共享的是「知识点本身」**（比如"乾内卦纳甲是甲子甲寅甲辰"这个事实）。这是不可避免的——审计经典规则时，预期只能来自经典。但本轮已把「共享知识点」压缩到最小：所有表都是我手写后与项目输出比对，**没有从项目代码里抄表**。

### 3.3 反例：一个差点误报的案例

`key-fact-audit` 曾判定「verdict.js 六冲卦只有 8 个，缺大壮、无妄」是错误。本轮查《增删卜易》原文（底本行 422）：

> 六冲卦者乾为天、坎为水、艮为山、震为雷、巽为风、离为火、坤为地、兑为泽，此八宫第一

**古法六冲卦就是 8 个八纯卦**。verdict.js 与原文一致，`constants.ts` 的 10 个才是六爻通行扩展定义。该问题从"错误"降级为"F6 流派分歧"。

这说明：**预期值必须来自可追溯的经典，不能来自"我觉得应该是这样"。**

## 5. 我修正自己预期的 3 处（完整留痕）

按任务书"禁止为了让测试通过而修改预期结果"，这里必须区分：**修的是我自己的预期错误，不是被测对象的错误**。三处修正全部有据可查：

### 5.1 第一处：T3 节气边界从 ±60s 改为 ±10min

- **初版**：节气时刻 ±0s / ±60s 三态
- **现象**：27 例月柱差异、6 例年柱差异，全部集中在 ±60s 内
- **分析**：astronomy-engine 与 lunar-javascript 的节气时刻本身差 60–120 秒（§3.3 已量化）。在 ±60s 窗口内，两套算法的"是否已交节"判断必然不同，这**不是逻辑错误，是基准精度差**
- **修正**：改用 ±10 分钟做"明确态"测试（96 例全通过），把 ±60s 的差异单独量化为"偏差表"（44 个切换点，最大 120s）
- **性质**：**修正测试设计缺陷**，不是放宽标准。因为原设计混淆了"逻辑错误"和"基准精度差"两件事

### 5.2 第二处：T4 时柱 23 点用次日日干

- **初版**：23 点的时干用当天日干起五鼠遁
- **现象**：5 例差异
- **分析**：晚子时 23:00 换日 → 日柱已是次日 → 时干必须按**次日日干**起五鼠遁。我的预期漏了这一步
- **修正**：`effDay = h >= 23 ? dayGZ(..., d+1) : dayGZ(..., d)`
- **性质**：**修正我自己的历法错误**。修完后 120/120 通过，说明被测实现是对的

### 5.3 第三处：T7 跨日 23:59 预期为次日

- **初版**：23:59 的日柱预期写"按同日"
- **现象**：2 例差异
- **分析**：同 5.2，晚子时 23:00 起日柱换日
- **修正**：`expDay = h >= 23 ? dayGZ(..., d+1) : dayGZ(..., d)`
- **性质**：同 5.2

### 5.4 一处保留的"差异"（不修预期）

`02_gua_paipan` 的 T2 有 1 例差异（雷火丰 `isGuiHun`）。**这一处没有修预期**，因为：
- 项目代码有明确注释说明这是主动覆盖
- 但覆盖结果与世位自相矛盾
- 因此**保留为差异并登记为待裁定问题**，而不是把它写成"预期"

这是本轮唯一一处"预期与被测不一致且未修改预期"的项。

### 2.2 P2：雷火丰归魂/世位（ISSUE-L0-001）

**这是本轮唯一需要主人做"体系选择"的问题，不能技术拍板。**

| 方案 | 做法 | 优点 | 缺点 |

### 2.4 P4：天机起卦概率（ISSUE-L0-004）

// input.ts castTianji 内，把均匀四象改为背数二项分布
