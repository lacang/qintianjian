## 二、入墓状态（`ruMu`）的计算：唯一来源，唯一布尔

`app/vendor/liuyao-core.js`：

```js
// :32974  function evalYao(input)  —— 每一爻的状态在这里一次性算完
// :33006
const cs = CHANG_SHENG[wuXing];
const at = (slot, z) => slot === z;
const ruMu = at(cs.mu, monthZhi) || at(cs.mu, dayZhi);
```

```js
// :32926-32930  十二长生表（土从火）
金: { zhangsheng: '巳', diwang: '酉', mu: '丑', jue: '寅' },
木: { zhangsheng: '亥', diwang: '卯', mu: '未', jue: '申' },
水: { zhangsheng: '申', diwang: '子', mu: '辰', jue: '巳' },
火: { zhangsheng: '寅', diwang: '午', mu: '戌', jue: '亥' },
土: { zhangsheng: '寅', diwang: '午', mu: '戌', jue: '亥' },
```

要点：

1. **`ruMu` 是一个布尔**，来源只有两种：月支等于该爻五行的墓库，或日支等于墓库。`monthZhi` 与 `dayZhi` 被 `||` 合并，**来源信息在计算时即被丢弃**——`state` 里没有任何字段记录「这个墓是月墓还是日墓」。
2. 判定口径是**十二长生墓位**（以爻的五行论），不是三合局墓库、也不是「随鬼入墓」。
3. 同一爻只有**一个** `ruMu` 值；不存在「同一爻有两个入墓事实」的可能（在现有模型里）。

## 三、对象同一性：用神持世时，两条规则读的是同一个对象

调用链（全部在 `app/vendor/liuyao-core.js` 的 `analyzeNajia` 内）：

```
paipan()                       → 本卦/变卦/纳甲/六亲/世应
analyzeNajia()
  ├─ 逐爻 evalYao()            → 每爻 state（含 ruMu）一次性生成        :32974 / :33006
  ├─ 构造 occ 对象             → { liuQin, pos, yao, naJia, moving, shi, state } :33155
  ├─ byLiuQin[liuQin].push(occ)                                        :33167
  ├─ an.shi  = { pos, occ: byLiuQin[shiLine.liuQin].find(o => o.pos===shiLine.pos) } :33182
  └─ yongshen[域].occurrences = qinWanted.flatMap(w => byLiuQin[w])    :33261
```

于是：

- `judgeNajia` 里 `yongOccs = ys.occurrences.filter(非伏神)`（多现时按 rank 取首，持世权重最高 8），`y = yongOccs[0]`；
- `an.shi.occ` 是 `byLiuQin[世爻六亲]` 中 `pos` 相同的那**一个**对象；
- 当用神六亲与世爻六亲相同、且 `pos` 相同（即「用神持世」），`y` 与 `an.shi.occ` 是**同一个对象引用**，因此 `y.state` 与 `an.shi.occ.state` 是同一个 `state` 对象，`ruMu` 是同一个布尔值。

全量场景实测（见 `05_全量统计报告.json` → `catC_detail.sameObjectIdentity`）：

> 双规则同爻共现的 4,352 个场景中，`y === an.shi.occ` **对象引用相同的有 4,352 个（100%）**。

这不是「两条规则恰好都判为入墓」，而是**同一条 `if (ruMu)` 判断被两个代码块各读了一次，各扣 1 分**。

## 四、评分汇总是否保留重复信号

`judgeNajia` 的信号汇总：

```js
const add = (w, text, src, qk) => { signals.push(...); score += w; ... };
...
return { level, ..., signals: signals.sort((a,b)=>Math.abs(b.w)-Math.abs(a.w)), ..., score };
```

- `score` 是**逐条 `add` 的线性累加**，没有任何按事实/按对象的合并；
- `signals` 数组保留全部条目，仅在展示层做「同 rule 只显示一次古文」的处理；
- 因此两条 `-1` 会实打实地把总分压低 2 分，且在信号清单里表现为两条不同文案（一条「用神逢入墓」，一条「世爻入墓」），**看起来像两条独立证据，实际是同一事实**。

## 六、规则—事实—对象—意义 对照表

| 规则 | 读取的事实 | 作用对象 | 表达的含义 | 是否与另一规则共享事实 | 初步判断 |
| --- | --- | --- | --- | --- | --- |
| 195 用神入墓 | `y.state.ruMu`（十二长生墓，月或日） | 用神爻 | 「所问之事被闭住、力量施展不开，须冲墓之月日才动」——**事的状态** | 是：用神持世时与 242 读同一对象的同一布尔 | **确认重复**（同对象、同事实、同来源、同分值方向；无语义差异可辨） |
| 242 世爻入墓 | `an.shi.occ.state.ruMu`（同一函数、同一表） | 世爻 | 「求测者自身被困、施展不开」——**人的状态** | 是：同上 | **确认重复**（同上） |
| 195 vs 242（用神**不**持世） | 两个不同对象的各自 `ruMu` | 两条不同爻 | 事 vs 人，两个独立事实 | 否 | **暂不构成重复** |
| 195 vs lost:434 | 同一 `y.state.ruMu` | 同一用神爻（妻财） | 通用「事被困」 vs 失物专项「物被藏」 | 是（同对象同布尔） | **疑似重复**（语义确实不同：一为事情进度，一为物品藏匿；但事实只有一个） |
| 242 vs health:358 | 世爻 `ruMu` vs 应爻空破墓绝 | 不同爻 | 人 vs 药/医 | 否（不同爻） | 暂不构成重复（需在 health 专项另审） |

判断依据说明：

- 「确认重复」的依据不是名称相似，而是**对象引用相同 + 事实字段相同 + 来源不可区分 + 两条规则在同一函数内先后无条件各扣 1 分**（第四、三节）。
- 「疑似重复」用于 lost:434：事实同一，但两条规则表达的是不同层面的判断意义（事情进度 vs 物品藏匿），古法上是否应各计一次需要单独论证，不在本轮下结论。
