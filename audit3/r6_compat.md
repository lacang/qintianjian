## 2. 微信内置浏览器的具体风险

> 微信 iOS = 系统 WKWebView（内核随 iOS 版本，**不受微信版本影响**）；微信 Android = X5→XWeb（内核随微信版本，**碎片化严重**）。以下 2.1–2.5、2.8 为静态证据可直接定论；2.6（键盘遮挡）、2.7（清缓存）、2.9（缩放手势）为基于规范的推断，需真机复核。

### 2.1 【致命】白屏无提示
`index.html:589` 只有一行 `type="module"`，全站无 `<noscript>`、无 nomodule 回退、无 `try/catch` 兜底 UI。任何一条语法不支持（`?.` / `??` / `||=`）都会让**整个应用不执行**，用户看到的是只有 `<body>` 背景色的空页。
- 复现：DevTools 里把 `js/baziview.js:124` 的 `||=` 换成不支持的语法即可复现（或直接在 iOS 13 真机打开）。
- 建议：加 `<noscript>` + 首屏 3 秒后仍未挂载则显示"请升级微信/系统"提示。

### 2.2 微信 iOS：跟系统走，iOS 13.3 及以下打不开
WKWebView 不独立升级，iOS 13.3/13.7 仍是 `?.`/`??` 可用但 **`||=` 不支持（需 14.0）** → 白屏。iPhone 6/6s/7 停在 iOS 12–13 的用户占存量不小。

### 2.3 微信 Android：内核分裂
- 微信 6.x/7.x（老 X5）：Chromium 53/57/66/77 → **白屏**。
- 微信 8.x（XWeb）：Chromium 86–107 → 可用，但 `:has()`（105+）与 `aspect-ratio`（88+）视具体版本，**同一台手机不同微信版本表现不同**。
- 建议：真机灰度，页面内 `navigator.userAgent` 打点比对。

### 2.4 日期输入框（13 处）
`input[type=datetime-local]` 在 iOS 14.5 以下没有原生滚轮，会渲染成一个显示 `1990-05-20T10:30` 的普通文本框；再叠加 `.tb-input{appearance:none}`（`style.css:1002`）把原生指示器也去掉了，用户没有任何"点这里选日期"的视觉线索。
- 另有一处不一致：`.mt-input`（`style.css:130`）显式写了 `color-scheme:dark`，而 `.tb-input`（`1001–1005`）**没写** → iOS 深色页面上弹出的原生日期滚轮会是浅色（白底），与全站深色割裂。
- 已在 Chromium 复现截断：输入框宽 152px，`08/01/1994, 11:` 之后被裁掉（时钟图标压住文字）——iOS 的本地化格式（`1994年8月1日 11:45`）更长，只会更糟。
- 建议：`font-size:16px` + 补 `color-scheme:dark`（或提供"年/月/日/时/分"五个 select 的降级面板）。

### 2.5 聚焦自动放大
（同 §2.4 同源）`.tb-input` 13px、`.cs-input` 13px、`.mt-input` 13.5px，**全部 < 16px**。iOS/微信 iOS 在聚焦时会强制把页面放大到 1.3–1.5 倍，且 `user-scalable=no` 自 iOS 10 起被忽略，挡不住。

### 2.6 `position:fixed` + 键盘
全站 0 处 `visualViewport` 监听。微信 iOS 键盘弹出时 `visualViewport.height` 变小而 `innerHeight` 不变 → 底部 tabbar（`.tabbar`，fixed，60px）与 toast/sheet 不会上移，会**盖住正在输入的框**；`css/tarot.css:305` 里 `bottom:calc(56px + env(safe-area-inset-bottom))` 的全屏牌桌同理。（推断，需真机确认具体遮挡范围。）

### 2.7 微信"清理缓存"与 SW
`sw.js` 对 HTML/JS/CSS 走**网络优先**（正确），`CACHE='qintian-v133'` 与 `?v=133` 一致，不会出现"改了代码用户看不到"。但微信设置里"清理缓存"会连 SW 一起清掉，弱网首屏会掉到无缓存状态。

### 2.8 外部依赖：**零 CDN、零外链字体** ✔
`index.html` / `sw.js` / `manifest.webmanifest` 内 `https?://` 命中 **0 处**；全站无 `@font-face`、无 Google Fonts。
- 断网/国内网络均可加载 ✔
- 代价：字体靠系统。`font-family` 首选 `Noto Serif SC`（Android 微信多数有），iOS 回落 `Songti SC`，都没有则 `serif` → 拉丁字母变 Times、中文可能变黑体，**排版会漂**但不影响功能。

### 2.9 其他
- `maximum-scale=1.0, user-scalable=no`（`index.html:4`）：iOS 微信里双指缩放仍生效（系统忽略该参数），但会挡住部分安卓机的无障碍缩放 —— 建议去掉。
- PWA（manifest / apple-mobile-web-app-*）在微信内**不生效**，只能"添加到桌面"到浏览器；不影响功能。

1. **行星符号颜色硬编码**：`js/astroview.js:23` `sun:'#f2b24b'`（月亮 `#dfe6f2` 等）写死在数据里，不读 `--cw-*`。深底好看，白底三套（羊皮卷/素绢/现代派）对比度 **1.38 / 1.64 / 1.87**，等于看不见（见 `390_astro_vellum.png`）。

3. **现代派星座符号 3.79**：`--cw-elF` 橙色 `#e65100` 在纯白上不达标（其余 11 套没问题）。

**修法**（不建议现在改）：给 `ASTRO_STYLES` 增加 `glyph` / `glyphAlt` / `pdeg` 三个变量，浅底皮肤单独指定深色值；至少让 `--cw-pglyph`/`--cw-pdeg` 从硬编码改为 `var(--cw-*, 原值)`。

## 5. 数据一致性

### 5.1 结果确定性（同输入连跑 20 次）——**一致 ✔**

引擎层（Node v26.12.1，直接 import `vendor/liuyao-core.js`，规范化 JSON 后取 SHA-256 前 16 位）：

| 系统 | 输入 | 运行 | 唯一哈希 | 哈希 | 字节 | 结论 |
|---|---|---|---|---|---|---|
| 紫微 `paiZiwei` | 1990-05-20 10:30 男（未传 tz） | 20 | **1** | `027ad80a39281c49` | 20531 | 逐字节相同 |
| 印度 `paipanVedic` | 1990-05-20 10:30 + 上海 31.2304/121.4737 +8 | 20 | **1** | `e5e5a3dc08f30f7e` | 11302 | 逐字节相同 |
| 西方 `paipanXingpan` | 同上 | 20 | **1** | `54e4069613a3c558` | 5552 | 逐字节相同 |

UI 层（真浏览器，`#view-*` `innerText` 取 SHA-256 前 16 位，每页连点 5 次重排）：紫微 / 星盘 / 吠陀 各 **5/5 相同**。

> 注意：紫微面板含"运限 · 大限与流年（丙午年 · 虚岁 37）"，**跨农历年比对会不一致**——这是"当前日期"字段，不是随机性，做逐字节比对时必须排除（本次同日内比对）。
> 三个排盘模块内无 `Math.random()`；`Date.now()/new Date()` 仅用于"此刻"默认值与流年高亮。

### 5.2 跨会话一致（清空 localStorage 后重排）——**一致 ✔**
清 `localStorage` + `sessionStorage` + 全部 `caches` + 注销 SW → 硬刷新 → 重新输入同一钟面时间 → 紫微渲染文本哈希 `aa1630f10299ecc7`，与清空前完全相同。**结果不依赖任何缓存状态。**

### 5.3 案例存取完整性——**无"整盘导出/导入"，只有复现码 ✔（设计如此）**

| 项 | 实测 |
|---|---|
| 导出/导入 UI | **不存在**（全站 0 处 `导出/备份/导入/Blob/FileReader/showOpenFilePicker`） |
| 持久化方式 | `localStorage` 存**复现码字符串 + 标题/副标题**，不含任何排盘字段（`js/cases.js:88 saveCase({kind, code, title, sub…})`） |
| 恢复方式 | 解码复现码 → 设 `panAt` → **重新计算**（因此"字段级比对"退化为"输入还原 + 重算一致"） |
| 容量 | UI 明示"星标不会被顶掉，其余自动保留最近 30 条" → **超过 30 条静默淘汰** |
| 实测 | 十几分钟点击操作后案例页已累计 **16 条**（每次排盘自动存一条） |

**结论**：本项验收要求的"保存→导出→清空→导入→逐字段比对"在**功能层面不成立**（没有导出/导入）。以实际存在的通道（复现码）替代测试的结果见 5.4：**同时区一致，跨时区不一致**。

复现码载荷实测（紫微 `QT1-JgEmVfMYAAGu`）：头部 1 字节（版本 4 bit + 类型 4 bit）+ 规则版本 1 字节 + **时间戳 4 字节（Unix 秒）** + 标志 1 字节 + 性别 1 字节。**无时区偏移、无经纬度**（紫微不带 `F_GEO`；星盘/吠陀带 lon/lat，但仍不带偏移）。
来源：`js/sharecode.js:223` `out.at = r.u32() * 1000;`（解码）、`:227` `if (flags & F_GEO) out.geo = {lon,lat}`。

### 5.4 时区依赖（关键项）

#### (a) 引擎层：显式时区参数 → 与系统时区无关 ✔
同一脚本在 5 个系统时区下各跑一遍，三套排盘哈希**完全一致**：

| 系统 TZ | ziwei | vedic | astro |
|---|---|---|---|
| `Asia/Shanghai` | 027ad80a39281c49 | e5e5a3dc08f30f7e | 54e4069613a3c558 |
| `UTC` | 同 | 同 | 同 |
| `America/New_York` | 同 | 同 | 同 |
| `Asia/Kolkata` | 同 | 同 | 同 |
| `Pacific/Kiritimati` | 同 | 同 | 同 |

→ **引擎没有隐式读系统时区**，`utcOffsetHours` 是显式入参，符合预期。

#### (b) UI 输入路径：换系统时区后手输同一钟面 → 同一盘 ✔
CDP `Emulation.setTimezoneOverride` 把页面时区从上海切到 `America/New_York`，重新输入 `1990-05-20 10:30` → 四柱 `庚午 辛巳 乙酉 辛巳`、hash `aa1630f10299ecc7`，**与上海时区下完全一致**。

#### (c) 复现码 / 案例：跨时区 → **不一致 ✘（P0）**

同一出生（上海 1990-05-20 10:30，码从该盘导出），同一复现码 `QT1-JgEmVfMYAAGu`，两次实测（各清空存储后冷启动）：

| 打开环境 | 时柱 / 时辰 | 四柱 | 紫微命宫 | 结论 |
|---|---|---|---|---|
| 上海（+8） | 辛巳 · **巳时** | 庚午 辛巳 **乙酉 辛巳** | 辛巳（仆役） | 原始盘 |
| 纽约（-4） | 甲戌 · **戌时** | 庚午 辛巳 **甲申 甲戌** | 癸未（另一宫） | **日柱退一天、时柱全变、12 宫整体错位** |

机制：码内只存**绝对 Unix 秒**，解码后按**打开设备的本地时区**还原钟面（`sharecode.js:223`），而紫微码连经纬度都不带（无 `F_GEO`）。所以"分享给外地朋友""换手机后重开案例""用户手机时区不是 +8"都会得到**另一个盘，且没有任何提示**。
- 影响：紫微/八字/星盘/吠陀全部走同一套 `panAt.birth`（绝对毫秒）→ 系统性问题，不是紫微独有。
- 建议：码内增补 `utcOffsetHours`（或 `tzName`）字段并参与版本校验；解码时用码内偏移而非设备本地时区。

#### (d) 静默兜底 +8 —— 引擎会告警，但**只有星盘页把告警显示出来**

`resolveTime()` 实测（1990-05-20 10:30 基准，除注明外）：

| 输入 | 结果 offset | 警告条数 | 评价 |
|---|---|---|---|
| 沈阳 城市 | **+9** | 1（"出生时值夏令时：钟面时间已减 1 小时…"） | **正确**——中国 1986–1991 夏令时已建模 |
| 沈阳 仅经纬度 | +9 | 2（+就近城市估算提示） | 正确 |
| 纽约 城市 | -4 | 2（DST 折算 + "北美夏令时 2007 年才改为现行规则，此年按现行规则近似"） | 正确 |
| 纽约 仅经纬度 | -4 | 3 | 正确 |
| 纽约 显式 `utcOffsetHours:-4` | -4 | **0** | 显式偏移不再折算，合理 |
| 伦敦 仅经纬度 | +1 | 3（含"EU 夏令时 1996 年才统一"近似提示） | 正确（BST） |
| 悉尼 仅经纬度 | +10 | 2（含"澳洲夏令时 2008 年才统一"） | 正确（南半球 5 月为冬令时） |

| **开罗 2026-07-15** | **+2** | **0** | **✘ 错**（埃及 2023 恢复夏令时，应为 +3），且**零告警** |

引擎侧的告警质量其实很高（连"历史 DST 规则按现行规则近似"都提示了）。问题在两处：

- **告警没送到用户眼前**：全站只有 `js/astroview.js:145` 渲染 `tzFallback` 提示；`baziview.js` 仅注释提到时区（`:32` 是缓存键），`ziweiview.js`/`vedicview.js` **完全不涉及时区**。→ 八字/紫微页用户**永远看不到**"+8 兜底"和"夏令时折算"提示。
- **时区表过期（数据问题）**：`liuyao-core/src/cities.ts` 把开罗标成 `dst:'none'`，而埃及 2023-04 已恢复夏令时（ICU 校验 `Africa/Cairo` 2026-07-15 = GMT+03:00）→ 2023 年后埃及出生/事件盘四柱整体差 1 小时，**静默**。同类：安曼/贝鲁特/大马士革/拉巴特未收录 → +8 兜底并告警（但四柱会错 5–11 小时，告警也救不回来）。
- 建议：把夏令时规则改为可更新的数据文件（或运行时用 `Intl.DateTimeFormat(tz)` 兜底校验一次，仅用于校验告警，不改变纯前端离线特性）。

### 5.5 数字精度——**无非法值 ✔**

对已出盘的 **10 个模块**（八字、紫微、星盘、吠陀、风水罗盘、藏历、塔罗、周易、天象、十二宫）逐页扫描 `innerText`：

| 检查项 | 正则 | 命中 |
|---|---|---|
| 度分进位越界（如 `29°60′`） | `(\d+)[°度]\s*(\d{1,2})[′']` 且分 ≥ 60 | **0** |
| 分秒进位越界 | `(\d+)[′']\s*(\d+)[″"]` 且秒 ≥ 60 | **0** |
| 浮点尾数泄漏（如 `23.799999°`） | `\d+\.\d{3,}` | **0** |
| 时分越界 | `[：:](\d{2}):(\d{2})` 且第二段 ≥ 60 | **0** |

实际显示形如 `Lahiri 23.73°`、`巨蟹 14°23′`、`甲子 · 23:00–00:59`，一位小数或整数分，无尾数。

**未覆盖**：梅花、奇门、大六壬、小六壬、阳宅、天球仪 6 个模块在自动化点击中未触发成盘（"起局/摇卦"等按钮文案与脚本匹配的 `排盘/起卦/抽牌/开始` 不一致），其度分秒输出未纳入本次扫描。
